# Data Provenance — Panta Signal

## Purpose

Panta Signal must make it clear where every important value comes from and whether it is source data, a deterministic derivation, or AI-generated interpretation.

## Mandatory Data Classes

### 1. Source Data

Data received from Panta or another explicitly documented external source.

Examples may include market identifiers, titles, probabilities, categories, status, volume/trade activity, and provider timestamps **only after those exact fields are verified against authoritative Panta contracts**.

Until that validation is complete, exact Panta field names and semantics remain **UNVERIFIED**.

### 2. Deterministic Derived Data

Values computed reproducibly from source observations or normalized records.

Examples:
- normalized timestamps;
- probability deltas;
- change rate / movement velocity;
- rolling-window statistics;
- abnormal-movement indicators;
- persistence metrics;
- related-market divergence;
- ranked signal scores.

Derived values must identify the algorithm/version and relevant input window or parameters.

### 3. AI-Generated Interpretation

Natural-language content produced by a model, such as:
- summaries;
- explanations;
- comparisons;
- suggested questions;
- narrative context.

AI interpretation is not source data and is not a deterministic signal. It must never be stored or displayed as if it were an original Panta value.

## Material Signal Traceability

Every material signal should be traceable to at least:
- provider/source identifier;
- market identifier;
- observation timestamp(s);
- local snapshot identifier(s) or equivalent reproducible inputs;
- algorithm name;
- algorithm version;
- calculation timestamp;
- parameters/window used;
- data-completeness state when relevant.

## Normalization Rules

Normalization should:
- preserve source identifiers;
- preserve original source timestamps where available;
- convert values only through documented deterministic rules;
- never infer missing source facts through AI;
- mark unknown/unsupported fields rather than silently substituting defaults with different semantics.

## Snapshot Rules

Snapshots exist to support time-based calculations and auditability.

A snapshot record should eventually identify:
- market identity;
- source/provider;
- observation/fetch time;
- provider timestamp if available;
- normalized values used by the Signal Engine;
- schema/version;
- ingestion/build version where practical.

Exact persistence schema is **PLANNED** and will be frozen in a later technical specification.

## Missing and Stale Data

Missing observations, delayed upstream responses, or stale snapshots must be visible to downstream calculations.

The system should not:
- fabricate intermediate observations;
- label stale data as current without a timestamp/status;
- let the AI Analyst manufacture values to close gaps.

Signal formulas must define how incomplete windows are handled before they are considered implemented.

## Related-Market Provenance

If future signals compare or cluster related markets, the relationship itself must be traceable. The system should record whether a relationship was:
- manually configured;
- deterministically matched by explicit rules;
- generated by an embedding/model-assisted process and then accepted under defined criteria.

Model-assisted grouping must not be presented as an authoritative source relationship without qualification.

## External Research Provenance

For hackathon rules, API documentation, or external facts, research notes should record:
- source title;
- source URL;
- access date;
- what was verified;
- whether the source is primary/authoritative or secondary.

## Current Verification State

The provenance model itself is defined. Exact Panta API field mappings, timestamps, endpoint semantics, and rate/availability behavior remain **UNVERIFIED** until Phase 1 authoritative validation.
